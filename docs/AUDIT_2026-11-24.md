# IProduction audit, 2026-11-24

Read-only audit of the repository at commit `fe443b9` (branch `claude/charming-ride-15y0ti`). No code, configuration, data or dependency was changed. The only files written are this one and `docs/AUDIT_QUESTIONS.md`.

**Independence:** the auditor (Claude) wrote most of this codebase earlier in the same working session. To limit that bias, every finding labelled VERIFIED was confirmed by a command or query run during this audit, not from memory of what was intended. READ-ONLY findings are inferred from reading the code and should be retested.

## 1. Summary

IProduction is a modular Laravel 13 / Livewire 4 / MySQL 8 manufacturing ERP for **one company per installation**. It covers sales, purchasing, batch production with PTCs (Product Travel Cards), contractor work, inventory, double-entry finance, payroll, 35 reports and go-live import. The core ledgers are sound:
- stock balances reconcile exactly to the append-only movement ledger (32 buckets, 0 mismatches);
- every journal balances, with one currency each;
- posted documents, journals and movements are locked at the model level;
- document numbers are race-safe and gapless.

**Top risks:**
1. **F-01 (High).** Stock valuation counts rejected production pieces twice. Stock at lot cost exceeds the Inventory account by exactly the rejected pieces' value: PKR 3,319.46 on the demo data. VERIFIED.
2. **F-02 (High).** After a partial PTC release, pieces still in production are valued at the released average cost while their cost is still in the PTC. Same double count. READ-ONLY.
3. **F-03 (Medium).** Excel and CSV exports write user-entered text such as `=HYPERLINK(...)` as live formulas. VERIFIED.
4. **F-07 / F-08 (Medium).** Nothing alerts anyone when a backup or scheduled job fails (no email or notification code exists), and backups are kept on the same server by default.
5. **F-05 / F-17 (Medium).** Nothing in code stops self-approval. Contractor stage work becomes payable without approval, unlike wage work.

**Top gaps:**
- no quotations;
- no landed cost for imports;
- no notifications or alerts;
- no shop-floor scanning or labels;
- no MRP across all orders, machines, capacity or maintenance.

**Top improvements:** fix F-01 and F-02; neutralise export formulas; add email alerts for failed jobs and pending approvals; block self-approval and add contractor approval; then quotations and landed cost.

**Decisions needed from you:** Q1–Q14 in `docs/AUDIT_QUESTIONS.md`. The most important are Q10 (how rejected pieces are valued), Q3 (imports), Q6 (self-approval) and Q4 (FBR).

## 2. Assumptions and what was not checked

- **Assumption 1:** single company, single plant, discrete batch manufacturing, made to order and to stock (from the data model and `AGENTS.md`). *If wrong:* multi-plant data separation becomes a Critical gap.
- **Assumption 2:** the local `iproduction` database may hold real data, so it was only read (SELECT). It holds 1 user and no transactions. *If wrong:* nothing changes; it was never written.
- **Assumption 3:** `iproduction_demo` is a scratch database loaded earlier with `DemoDataSeeder`. It was used, read-only, for reconciliation. *If wrong:* reconciliation figures describe demo data, not your data.
- **Assumption 4:** "valuation" means stock at lot cost, as the Stock summary report defines it. *If wrong (for example standard cost):* F-01 and F-02 change in form, not in substance.

Not checked, and why:
- **Production servers, hosting and real backups:** no access.
- **Real business data:** none exists locally.
- **The 5 newest migrations on the local databases:** `iproduction` and `iproduction_demo` are both 5 migrations behind the code (worker rates, export fields, depreciation). Migrating was forbidden, so reconciliation on those features relies on the automated tests, which run on `iproduction_test`.
- **Browser and UX testing on shop-floor devices:** no device testing in this pass.
- **Full password-reset and session-revocation flows:** only configuration was read (READ-ONLY).
- **Log contents for secrets or personal data:** no production logs available.
- **Lookalike or typosquat package names:** not checked beyond the vulnerability audit.

## 5. Process flows

| Flow | Works | Dead ends and manual workarounds |
|---|---|---|
| Quote-to-cash | SO (draft → approved) → planning (reserve, PO, PTC) → delivery (allocate → pack → dispatch: stock out, Dr COGS) → invoice (posted: Dr AR / Cr Sales + tax) → receipt (customer currency, deductions, advances) → currency conversion (typed PKR). Traced in `tests/Feature/Delivery`, `tests/Feature/Finance`; the demo data runs the whole flow (VERIFIED: receivables EUR 2,010 = AR account EUR 2,010). | **No quotation step:** quotes are made outside the system, or as draft orders plus the proforma print. **No debit note:** extra charges need a journal voucher. |
| Procure-to-pay | PO → GRN (posts stock and Dr Inventory / Cr AP; rejects returned or kept) → vendor bill (tax, charges) → payment. | **No requisition:** requests are verbal or paper. Bill rate isn't checked against the PO rate (2-way only). Import duty and freight become expenses, not material cost (no landed cost). |
| Plan-to-produce | Planning shortfall → PTC (approve copies route and BOM) → material issue → stage issue and receive (wage work or contractor payable) → release (cost to output lot) → complete (late cost settled). | No MRP across orders: one line at a time. **Contractor stage work posts the payable without approval** (F-17). Rejected pieces keep full lot cost (F-01). |
| Inventory lifecycle | Receive (lot created) → reserve → allocate or issue → count and adjust (Dr/Cr Inventory) → valuation report. Reconciliation VERIFIED (section 7). | Valuation report disagrees with the Inventory account (F-01). |
| Returns and rework | Delivery return → restock or send to rejections → credit note; purchase return; rejection decisions (scrap and others). | No rework order linking rejected pieces back to a PTC (rework is handled as a new PTC by hand). |

## 8. Reporting audit

**Inventory:**
- 35 reports (`app/Modules/Reports/Definitions/*`), each with screen, print, PDF, Excel and CSV through one shared screen.
- All on demand; nothing scheduled or emailed.
- Access requires `reports.view` plus each report's own permissions (`Reports.php:28-40`). The full list with permissions and filters is in the verification log (section 13, command C14).

Other outputs:
- 20 document printouts, each checking `{resource}.print` on its route;
- dashboard tiles;
- Excel/CSV export on every list.

**Correctness (VERIFIED on demo data):**

| Report | Check | Result |
|---|---|---|
| Receivables | vs `accounts_receivable` account per currency | EUR 2,010 = 2,010; USD 0 = 0 |
| Customer sales | vs posted, non-cancelled invoices | USD 7,900 = 7,900; EUR 4,184 = 4,184 |
| Stock summary and valuation | Value = Σ quantity × lot cost, all statuses (`StockSummary.php:65`) | **Overstated by rejected PTC pieces (F-01)** |
| Trial balance, P&L, balance sheet, cash flow, tax summary, customer profitability | Automated tests: balance sheet balances, cash-flow closing = cash and bank balance in PKR, USD and EUR, tax and profitability figures (`tests/Feature/Finance/AccountingDepthTest.php`, `tests/Feature/Reports/BusinessReportsTest.php`) | Pass in the test suite (section 13) |

**Edge cases:** date filters use `startOfDay`/`endOfDay` and are inclusive (`Report.php:111-131`). Reports on posted documents filter on `posted_at` and `cancelled_at`. The PTC transaction reports (stage work, wastage, rejections) correctly have no status filter, because transactions take effect when recorded.

**Authorization:**
- Server-side per report, and per document print route.
- No per-object scoping is needed: there is no multi-plant or ownership model.
- Trial balance needs only `ledgers.view`, while P&L and balance sheet also need `profit.view` (F-12). Inconsistent, low risk.

**Performance:**
- Every report builds all rows, then paginates in memory (`Reports/Livewire/Show.php:64-71`).
- Order costing runs about 20 queries per order line: measured earlier in this session at 185 queries for 9 lines. That affects Order cost and Customer profitability (F-06).
- Filter columns are indexed.

**Export safety:** formula injection (F-03). Exports run synchronously, and temporary files are handled by maatwebsite/excel.

**Consistency:** dashboard and reports read the same ledgers. Metric definitions are written in each report's `description()` and notes. The valuation disagreement (F-01) is the one inconsistency found.

**Missing reports**, justified by the business profile:
- stock ageing by value;
- production plan vs actual by day or week;
- supplier on-time delivery;
- receivables and payables ageing buckets as their own report (partly covered by Receivables days and buckets, and Bills due);
- labour efficiency (no standard times exist, so it can't be computed);
- daily production summary per stage (partly covered by Stage-wise work).
